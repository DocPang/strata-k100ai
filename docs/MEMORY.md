# 显存、上下文与并发

## 容量构成

单卡实例的 GPU 内存主要由专家、dense 权重、目标模型与 MTP 状态、KV、prefill 工作区、图与运行时缓冲构成。系统内存还承担专家 mmap/页缓存、PLE 页缓存、KV streaming 的锁页内存及会话缓存。

容量规划应以加载日志和运行峰值为准。权重文件大小、专家数据大小、稳定运行占用和加载峰值是不同指标。

## IQ3_S 与 IQ3_XXS

固定上游指纹表中的专家原始数据量为：

| 权重 | 专家原始数据 | 相对 IQ3_S |
| --- | ---: | ---: |
| IQ3_S | 46.8384 GiB | — |
| IQ3_XXS | 39.9658 GiB | 少 6.8726 GiB |

来源：固定版本 Strata 的 [gguf_fingerprints.json](https://github.com/Niko1221/Strata/blob/fb58e0dbc8399662c0e47c76578c6e878b14f6cf/data/gguf_fingerprints.json)。该表不包含全部 GPU 内存开销，也不代表加载峰值。

XXS 为工作区和上下文状态提供更多容量，但更换量化会改变数值结果及内核分派。需要为 XXS 重新生成 pack。减少专家字节数不直接保证端到端速度提升。

## 四类参数的区别

| 参数 | 主要影响 | 调节要点 |
| --- | --- | --- |
| --expert-cache | 专家驻留容量与数据搬运 | 24576 为本模型全部专家槽；减少后可能出现 CPU/主存到 GPU 的专家搬运 |
| --prefill | 分块输入计算与临时工作区 | 降低可减少工作区，长输入会分成更多块 |
| --max-context | 会话容量及上下文相关状态 | 包含输入、历史、模板与输出；减小后长请求会被拒绝 |
| --kv-resident | KV 显存驻留缓存 | 0 表示完整驻留；非零时有效容量至少 20480 |

`--vram-reserve-mib` 是规划阶段的预留，不是显存回收开关。降低预留可能减少瞬时分配余量；提高预留可能影响专家驻留或使配置无法装载。

## INT8 KV 估算

对于本模型的 12 个 QSA 层，INT8 K/V 主体按每层每 token 1056 字节估算：

```text
QSA KV 主体字节数 ≈ token 数 × 12 × 1056
```

| token 数 | QSA KV 主体理论值 |
| ---: | ---: |
| 20480 | 247.5 MiB |
| 32768 | 396 MiB |
| 65536 | 792 MiB |
| 131072 | 1.547 GiB |
| 262144 | 3.094 GiB |

该估算不包含分配对齐、预取缓冲、索引器、GDN 状态、MTP、prefill、图或服务缓存，不能作为总显存预测。

使用 `--max-context 262144 --kv int8 --kv-resident 32768` 时，完整 KV 在宿主 pinned RAM 中保存，GPU 维持驻留缓存。超过驻留容量的数据按运行时需求传输，完整上下文不会被截断为 32K。驻留缓存不是语义滑动窗口。

即使 GPU KV 驻留容量固定，扩大 `max-context` 仍会增加 pinned RAM 和部分 GPU 状态开销；长上下文的检索、传输与计算成本也会增长。

从 32768 降至 c4 下限 20480，QSA KV 主体理论上减少 **148.5 MiB**。对数 GiB 的显存缺口，应优先检查权重、prefill、上下文状态及其他进程，而不是仅缩小 KV 驻留。

当 `kv-resident=0` 或上下文不超过有效驻留容量时，不启用上述 streaming。将 256K 配置从 32K 驻留改为全量 KV 驻留，QSA KV 主体理论上增加约 **2.707 GiB** GPU 内存，其他开销另计。

## 调整顺序

1. 确认目标卡空闲，记录加载阶段与首轮长请求峰值。
2. 保持 `expert-cache=24576`，先将 `prefill` 从 20480 降至 8192；必要时再测试 4096。记录 TTFT 和总 prefill 时间。
3. 按业务长度设置 `max-context`。只需要 64K 时使用 65536，无需为所有实例预留 256K 状态。
4. 在主存和传输允许时保留 KV streaming。驻留容量可在 32768、20480 等值之间实测；低于 20480 不会继续按比例减少有效缓存。
5. 使用 XXS 时，先维持相同上下文与驻留配置建立基线，再评估提高 prefill 或全量 KV 驻留。每次只调整一项。
6. 仍不足时再评估减少专家驻留量。此调整可能显著降低解码速度，应与更小权重方案分别比较。

以下为调试起点，不是不同机器上的最优参数保证：

| 场景 | max-context | prefill | kv-resident | 取舍 |
| --- | ---: | ---: | ---: | --- |
| 发布参考配置 | 262144 | 20480 | 32768 | 保留长上下文，工作区需求较高 |
| 工作区受限 | 262144 | 8192 | 32768 | 减少单块工作区，prefill 分块更多 |
| 中等长度业务 | 65536 | 8192 | 32768 | 降低上下文状态和宿主 KV 容量 |
| 全量 KV 对照 | 262144 | 8192 | 0 | 增加显存需求，用于与 streaming 比较 |

## 请求长度与输出空间

`max-context` 包含输入及输出。服务还保留内部 token 余量，不能提交等于配置上限的正文后再要求生成。当前服务使用 8-token 余量；在 262144 上下文和 4096 最大输出下，模板化输入上限为 258040 token。正文字符数不能替代 tokenizer 计数。

## 系统内存与缓存

- KV streaming 使用 pinned RAM，应同时观察 RSS、锁页内存与系统可用内存。
- `--conversation-cache-mib 16384` 为宿主会话缓存预算，不是显存配额。
- `--conversation-cache-slots 4` 是缓存条目数，不是四路同时解码。
- 主存压力引发的 mmap/PLE 页缓存抖动可能表现为 GPU 利用率下降及 TTFT 波动。

## 并发与多卡

本版本提供单卡配置。增加 API 客户端数量不等于增加同时解码槽；排队行为与真正 batch 需要分别测试。`--batch`、`--batch-mtp` 会增加会话状态及 MTP 开销，未包含在本版本的参考配置中。

两张卡分别启动独立实例时，各自加载模型、管理缓存并使用独立端口。TP2 会改变通信和计算路径，不能由两个单卡实例的结果推断其效率。
